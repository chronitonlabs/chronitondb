## 1. Purpose and scope

ChronitonDB is a fork of Apache Cassandra, and its builds carry a version of their own, `<Apache version>-chronitondb<n>`, next to the Apache version they contain ([release.md](../../process/release.md#version-numbers)). Nothing in the build or in a running node knows that version today: the build writes only Apache's `CassandraVersion` and `GitSHA` into `version.properties` (`build.xml:492` to `499`), and `nodetool version` prints only Apache's release version (`src/java/org/apache/cassandra/tools/nodetool/Version.java:36`). An operator rolling a cluster from one ChronitonDB release to the next cannot ask a node which ChronitonDB build it runs.

This feature adds that. The build writes a `ChronitonDBVersion` entry into `version.properties` after Apache's two entries, a node serves it over JMX from an MBean in the `org.chronitondb` domain, and the new command `nodetool chronitondbversion` prints it as one line, for example `ChronitonDBVersion: 5.0.10-chronitondb1`, for the node it connects to. The command takes the global options every nodetool command takes, host, port, user name, password, password file and print port (`src/java/org/apache/cassandra/tools/NodeTool.java:351` to `367`), and no option of its own, and asks one node, as `nodetool version` does.

A line is a trunk of the fork per Apache major version ([branching-and-review.md](../../process/branching-and-review.md#the-lines)). This feature targets the `chronitondb-sandbox` line only, the throwaway line of the process dry run, and exists to exercise the development process end to end on it. The line has no release. The feature is subject to the final gate like any other feature, and no release ever carries it, so nobody runs it outside the line's own builds and tests. No other line gets it.

In scope: the version entry, the `BuildVersion` class with its MBean, its gate field and the lift, the three commands (`nodetool chronitondbversion` and the two toggles), the switch with its yaml setting and toggles, the counters and the INFO lines the checklist of quality-requirements.md asks for, the tests, and the reference documentation.

### Non-goals

1. Printing Apache's release version or the git SHA from this command. `nodetool version` prints them already (`Version.java:36` and `:38`), and the chosen shape is one line (decision record 0002). The command has no `-v` option. Nodetool refuses one through its stock usage error.
2. Changing what `nodetool version`, `bin/cassandra -v`, `system.local`, gossip or the drivers report. Those carry Apache's release version today and are stock behaviour. The node reported version form of [release.md](../../process/release.md#the-version-a-running-node-reports), a planned second string that a node will report in those places, is a separate feature.
3. Reporting the version of the nodetool jar itself. The command reports the node it connects to, as every nodetool command does (decision record 0002).
4. A virtual table, a cqlsh command or a native protocol change carrying the version. Nobody asked for one. The switch appears as a row of `system_views.settings` like every `Config` field, see section 2.6, and that row carries the switch, not the version.
5. Creating the fork's own configuration file, `conf/cassandra_chronitondb.yaml` of [release.md](../../process/release.md#the-configuration-file), which this line does not have. The switch's default lives in its `Config` field, and the file is for the maintainers to introduce with the release process, see section 2.6.

## 2. Architecture

### 2.1 Context and scope

The operator's nodetool talks to one node over JMX, as for every nodetool command (`NodeTool.java:390` and `:444`). The node answers from a string it read from `version.properties` through its own class loader. No other node, client or external system is involved.

### 2.2 Building blocks

Test code only, see section 2.5 |

### 2.3 Runtime view

1. Build: every target that runs `_createVersionPropFile` writes `ChronitonDBVersion=<Apache version>-chronitondb<n>` into `version.properties`, after `GitSHA`, the last of Apache's two entries (section 2.4).
   1. `<Apache version>` is the `base.version` property (`build.xml:36`), never the `${version}` form, which stock writes into `CassandraVersion` and which carries `-SNAPSHOT` unless the `release` property is set (`build.xml:104` to `107`). The two properties are independent: a build with neither `release` nor `chronitondb.release` set writes `5.0.10-chronitondb0` next to `5.0.10-SNAPSHOT`.
   2. `<n>` is the release number: the value of the ant property `chronitondb.release` from any ant property source, for example the command line `-Dchronitondb.release=1` or `build.properties` (`build.xml:30` to `31`), with the white space around it trimmed. The property unset, empty or made of white space only gives `0`.
   3. A trimmed value that is not a release number, as the glossary defines it, fails the build inside `_createVersionPropFile` with an error that names the property, so only a target that writes the entry fails. The build trims and checks the value by the glossary's definitions, and the ant mechanism that does so is settled in the design record of the item that edits `build.xml`.
   4. The entry carries the trimmed value. It does not tell a build given `0` from a build given no number, and nothing else marks either case. A release always has a release number of 1 or more ([release.md](../../process/release.md#version-numbers)), so `0` names an unreleased build.
2. Startup: `StorageService.initServer` (`src/java/org/apache/cassandra/service/StorageService.java:967`), through the hook call placed right after the four stock log lines at `:969` to `:973` and before the `try` at `:975`, creates `BuildVersion`, one object per node. That call is the node start of the glossary, and what the call does for this feature, creating `BuildVersion` and steps 4 and 5 below, is the startup step of the glossary.
   1. A real node reaches it through `CassandraDaemon.setup` (`src/java/org/apache/cassandra/service/CassandraDaemon.java:383`). An in-JVM test instance calls it only when it starts with the framework's GOSSIP feature (`test/distributed/org/apache/cassandra/distributed/impl/Instance.java:704` and `:709`, the other branch at `:723` to `:740` ends in `completeInitialization` and never calls it). The unit test JVM calls it when a test starts its services (`test/unit/org/apache/cassandra/cql3/CQLTester.java:633` to `638`). `initServer` runs once per JVM: stock's own second call would fail at `registerMBeans` (`StorageService.java:1018` and `:560` to `564`, with `MBeanWrapper.java:85` to `88`, `:176` to `185` and `:365`), and `CQLTester` guards its call (`CQLTester.java:624` to `625`), so the hook has no second call to handle.
   2. An in-JVM instance started without GOSSIP has no `BuildVersion` and no MBean, so every in-JVM distributed test of this feature starts its instances with the GOSSIP and JMX features (FREQ-BVER-023).
   3. By then the stock yaml loader has set the switch to its yaml value, the only startup source of the switch.
   4. While the gate field is false, `BuildVersion` first sets the switch to false, whatever the yaml value, and logs that at INFO with the old and the new value, also when both are false (FREQ-BVER-032). That is the only startup log line of the feature: while the gate field is true the switch keeps the yaml value and nothing logs it.
   5. Only after that step does `BuildVersion` register the MBean and the two counters, so no read is served before the step has run.
   6. The gate field and that startup step stay in the code after the gate field turns true. Step 4 then does nothing and the switch keeps its yaml value, while the MBean and the counters are registered as before (step 5).
3. Version read: the switch check and the counters sit inside `BuildVersion`, so every caller of its version read, over JMX or by a Java call, is refused and counted alike. Shipped code has no Java caller of it.
   1. On the first read the switch serves, `BuildVersion` loads `version.properties` through its own class loader, `BuildVersion.class.getClassLoader()`, as `FBUtilities` does for Apache's keys (`src/java/org/apache/cassandra/utils/FBUtilities.java:444`). It has hand written one time loading code of its own, since the memoized supplier `FBUtilities` uses is private to it (`FBUtilities.java:443` to `458`), and it loads once even when two first reads arrive at once.
   2. The loading code of `BuildVersion` takes the properties stream as its input, and no stream when the file is absent from the class path, so a unit test feeds it each case of FREQ-BVER-006 without a served read.
   3. The node's version is then the trimmed value of the entry, whatever its form, since the build checks the form (FREQ-BVER-003), or `Unknown` when the node cannot read one, and `BuildVersion` keeps it for the life of the node with no later retry. It logs nothing about the load in any case, since the value `Unknown` makes a missing entry visible.
   4. A refused read loads nothing and logs nothing: the counter records it.
   5. `nodetool chronitondbversion` connects and reads `Version`. With the switch on the node returns the node's version and counts `ReadsServed`, and the command prints `ChronitonDBVersion: ` followed by it on stdout and exits with status 0.
   6. With the switch off the node answers with the read refusal and counts `ReadsRefused`, and the command prints nothing on stdout and reports the refusal through the stock error path, with the node's message, which names the setting, in the text on stderr.
4. Toggles: `nodetool enablebuildversioncommand` writes `Enabled` to on, `nodetool disablebuildversioncommand` writes it to off. The gate refusal is the only refusal the feature's own code makes of a write, apart from what stock JMX authorisation refuses before the write reaches the MBean: every other write of `Enabled` is an accepted write. On an accepted write the node changes the `Config` field in memory, logs the old and the new value of the switch at INFO, also when they are equal, and the command prints nothing and exits with status 0, like stock `nodetool enablehandoff` (`src/java/org/apache/cassandra/tools/nodetool/EnableHandoff.java:28` to `32`). While the gate field is false a write to on gets the gate refusal: the switch stays as it is, the node logs the refusal at INFO (FREQ-BVER-028), and the toggle reports the refusal through the stock error path. A write to off is accepted in every state.
5. No coordinator, replica, memtable, flush, compaction, streaming or repair path is touched.

### 2.4 Data and formats

The one new entry in `version.properties`, a file on the class path. No data file on disk, no wire form, no schema and no cluster metadata is added or changed. Stock reads the file in two places. `FBUtilities` reads it by key (`FBUtilities.java:465` and `:473`) for the node, `nodetool version` and `bin/cassandra -v` alike, so the new entry changes nothing for them. `cassandra-stress version` reads the whole file as one string and matches it with the pattern `.*?CassandraVersion=(.*?)$` and no flag (`tools/stress/src/org/apache/cassandra/stress/settings/SettingsMisc.java:134` to `135` and `:148`), so its result depends on the line order of the file: without the multiline flag `$` matches only at the end of the file, so the pattern finds the version only when `CassandraVersion` is on the file's last line, and otherwise the command prints `Unable to find version information` (`SettingsMisc.java:155`). The build writes `CassandraVersion` first and `GitSHA` after it, in the order of the entries of the `propertyfile` task (`build.xml:496` to `497`, the order observed with Ant 1.10.15), and the new entry goes after `GitSHA`. On a file in that order `CassandraVersion` is not the last line, and the entry after `GitSHA` leaves that as it is, so the command prints the same text on a build of the merge commit of the item that adds the entry as on a build of that item's base commit, when both builds use the same ant target and properties from a clean workspace, since the file survives between builds (FREQ-BVER-026). Which of the two texts a base build prints is stock's behaviour, which this spec does not assert and the comparison does not depend on. A validation item compares the two outputs, in the way its design record says. A difference fails FREQ-BVER-026 and is fixed through change control of this spec, since the position is approved with it. The position holds for a fresh file and for a file an earlier build left behind, since the task appends a new key at the end of an existing file too (observed with Ant 1.10.15).

### 2.5 Cross cutting concepts

1. Settings: one yaml setting, `build_version_command_enabled`, a `volatile` primitive `boolean`. Stock refuses a yaml key it does not know (`src/java/org/apache/cassandra/config/YamlConfigurationLoader.java:422` to `423`), so the setting is a `Config` field. The stock loader leaves a field whose key is absent at its initial value, `true` here, the default, and refuses a key given no value (`YamlConfigurationLoader.java:370` to `376` and `:419` to `420`).
2. Limits: none. A read returns one string held in memory.
3. Observability: the counters `ReadsServed` and `ReadsRefused` of the metric type `BuildVersion`, one INFO line with the old and the new value of the switch for every accepted write of `Enabled` and for the startup step of section 2.3 item 2 while the gate field is false, also when the two values are equal, and one INFO line for every refused write. Each log line names the setting, unlike the gate refusal text sent to the client (item 4): a bound the design record of the item that builds `BuildVersion` meets within the exact texts it settles, not a requirement of section 3. The outcomes of a write, accepted and refused, are logged and not counted: a write is one operator action behind JMX authorisation and its INFO line is the record, so the feature's counters are the two of the version reads, the one path a request takes. A read of `Enabled` is neither counted nor logged: it changes nothing and serves the toggles and the tests. No trace line, since the feature makes no query plan decision and has no fallback. The MBean and the counters live for the life of the node, so there is nothing to release.
4. Error handling: the read refusal names the setting `build_version_command_enabled` and no toggle or other command, in every state: the setting is the one name that is right before and after the final gate, and before it the toggle is refused, so the message never sends an operator there. The gate refusal says that the build predates the feature's final gate, which is true of every build whose gate field is false, before and after the report's merge, and names no setting or toggle, since none controls the gate field. The exact text of each is settled in the design record of the item that builds `BuildVersion`, within these bounds. Each is a class of the Java platform under `java.*` or `javax.*` that extends `RuntimeException`, so that a JMX client without the ChronitonDB jar, such as jconsole or a metrics agent, deserialises it rather than a `ClassNotFoundException`, the advice stock's own MBean test quotes (`test/unit/org/apache/cassandra/tools/JMXStandardsTest.java:90` to `95`). Each is neither `IllegalArgumentException` nor `IllegalStateException` nor a subclass of either, which nodetool treats as usage errors (`NodeTool.java:277` to `288`), so that it reaches the stock error path. `UnsupportedOperationException` meets both bounds and is one choice. The design record names the class of each refusal within the bounds, the same class for both or one each (FREQ-BVER-035). Each carries the node's text as its own message with no cause, since the stock error path prints the message of the root cause (`NodeTool.java:291` and `:330`), and the two refusals are told apart by their text. A version the node cannot read is `Unknown`, the stock idiom for a missing `GitSHA` (`FBUtilities.java:118` and `:473`). There is no system property override of the ChronitonDB version, unlike stock's own two keys (`FBUtilities.java:464` and `:472`).
5. Security: the MBean sits behind the node's JMX authentication and authorisation like every stock MBean (`conf/cassandra-env.sh:237` to `247`, `src/java/org/apache/cassandra/auth/jmx/AuthorizationProxy.java:79`). Both are opt in. By default `LOCAL_JMX` is `yes` (`cassandra-env.sh:228` to `230`), which binds JMX to the local host with authentication off (`cassandra-env.sh:238` to `239`), and the authorisation proxy is a commented line (`cassandra-env.sh:275`), so on a default node any local JMX client can read the version and toggle the switch, as it can read and change every stock MBean. The reference page says so. Where the proxy is on, it matches granted names with `ObjectName.apply` and no test of the domain (`AuthorizationProxy.java:389` to `405`), so `org.chronitondb` is covered like any domain, and stock authorises per MBean, a read of an attribute with `SELECT` and a write with `MODIFY` (`AuthorizationProxy.java:422` to `427`), so a role needs `SELECT` on the version MBean for `nodetool chronitondbversion` and for a read of `Enabled`, and `MODIFY` on it for the toggles. The counter MBeans need no permission for the commands to work. Section 6.3 and the reference page state it.
6. Gate: before the feature's final gate the switch refuses to turn on ([branching-and-review.md](../../process/branching-and-review.md#feature-switches-and-defaults), rule 2). The final gate is the merge of the milestone report of milestone 1, this feature's only milestone ([additive.md](../../process/additive.md#milestone-gates)).
   1. The code knows nothing of that merge. It reads the gate field, the private static boolean `finalGatePassed` of `BuildVersion`, read at run time and never a compile time constant, and the requirements of section 3 are written against that field.
   2. Every build on this line carries false in it until a one line code change, in a pull request a maintainer merges after the report, sets it to true. The process pages on this line define no step that makes that change. Which step makes it, and whether it is an item of this feature's plan, is for the maintainers to decide before the plan is written, and their answer becomes a decision record. Until that change exists the switch stays off for anyone who runs a build of this line.
   3. Tests get past the gate field's refusal only through the lift, which sets the field to true by reflection inside each instance's class loader before the instances of a cluster start, so a lifted cluster starts with the field true on every instance.
   4. The in-JVM framework loads a class per instance unless the class carries the framework's `Shared` annotation or the framework's default filter names it (`test/distributed/org/apache/cassandra/distributed/impl/AbstractCluster.java:1161` to `1166` and `:1186` to `1197`), so `org.chronitondb` classes, their static fields included, load per instance like `org.apache.cassandra` ones unless that filter names them, which risk R7 has the design record check.
   5. The lift is the only test code that touches the field: no unit test sets it, so tests of the switch on state exist only as in-JVM distributed tests. Shipped code has no setter and no other path to the field but the one line change (FREQ-BVER-027, [testing.md](../../process/testing.md#scenarios), rule 9).

### 2.6 Deployment

1. New yaml key `build_version_command_enabled` for an operator's `cassandra.yaml`. Its yaml value is `true` when the key is absent, the default, so an operator on a build whose gate field is true does nothing to turn the feature on, and the toggles change it at runtime. On every build of this line as written the gate field is false, so no operator can turn it on (section 2.5 item 6). The sandbox line ships no `conf/cassandra_chronitondb.yaml`, the fork's own configuration file of [release.md](../../process/release.md#the-configuration-file), that file is not in the scope of section 1, and Apache's two yaml files stay untouched, so no configuration file in the tree carries the key. An operator who wants the feature off adds `build_version_command_enabled: false` to the node's `cassandra.yaml`.
2. New nodetool commands `chronitondbversion`, `enablebuildversioncommand` and `disablebuildversioncommand`.
3. New MBean `org.chronitondb:type=BuildVersion` and the two counter MBeans `org.chronitondb:type=BuildVersion,name=ReadsServed` and `org.chronitondb:type=BuildVersion,name=ReadsRefused`, all three in the fork's JMX domain and none in Apache's.
4. A new row `build_version_command_enabled` in `system_views.settings`, which lists every `Config` field (`src/java/org/apache/cassandra/db/virtual/SettingsTable.java:59` and `:153` to `154`), showing the switch's value, `false` while the gate field is false.
5. No new file on disk.

### 2.7 Package dependencies and hook points

A name without a star covers that one package, and a name ending in `.*` covers the package and its subpackages. Test code under `test/` is not bound by it. The names in brackets are notes on what the feature uses from each package and bind nothing.

### 2.8 Feature class and switches

Feature class: purely additive, because the feature is reachable only by asking for things stock Apache Cassandra does not have, a nodetool command that stock nodetool refuses as unrecognised, a yaml setting that stock refuses at startup, and an MBean that stock does not register, and because it changes no stock operation. The feature class rule of [branching-and-review.md](../../process/branching-and-review.md#feature-switches-and-defaults) names new syntax, new index types and new settings as the ways a purely additive feature is reached. This spec reads that list as examples of things stock does not have, which a new command and a new MBean are too. A maintainer approves the class with the spec ([branching-and-review.md](../../process/branching-and-review.md#feature-switches-and-defaults), rule 6), so the merge of this spec approves that reading and the class.

| Switch | Class | Reason | Default per line | Stock operations it changes |
|---|---|---|---|---|
| `build_version_command_enabled`, toggled by `nodetool enablebuildversioncommand` and `nodetool disablebuildversioncommand` | purely additive | It gates only the `Version` read and `nodetool chronitondbversion` | `chronitondb-sandbox`: on | none |

The default is the yaml value the switch takes when the yaml key is absent, in every state. The switch takes the yaml value as its startup value once the gate field is true. While the gate field is false the switch is off on every node, whatever the yaml value: FREQ-BVER-015 and FREQ-BVER-016 govern the startup value and the writes then, and FREQ-BVER-009 governs the startup value once the field is true. FREQ-BVER-010, the yaml value when the key is absent, holds in every state. The setting and the toggles are named for what they gate, the build version command, after Names rule 2 of [conventions.md](../../process/conventions.md#names), the command for what it prints, the MBean type and the metric type for the class that serves both, and the counters for what they count.

What a user who sets no ChronitonDB key and runs no ChronitonDB command sees with the feature present and the switch off, which is every node of this line while the gate field is false:

1. `nodetool help` lists three more commands, `chronitondbversion`, `enablebuildversioncommand` and `disablebuildversioncommand`, because one command list (`NodeTool.java:98` to `246`) feeds both the parser and the help command (`withDefaultCommand(CassHelp.class)` at `:251` and `withCommands(commands)` at `:252`).
2. `SELECT * FROM system_views.settings` returns one more row, `build_version_command_enabled`, with the value `false` (`SettingsTable.java:59` and `:153` to `154`).
3. The JMX tree has the domain `org.chronitondb` with the version MBean and the two counter MBeans of the metric type `BuildVersion`, and no new name in any stock domain.
4. The node holds in memory the `BuildVersion` object, its MBean registration and the two counters, and after the first served read the version string: a fixed set of objects that grows with no request and no data.

Nothing else: no thread, no file, no log line but the one startup line of section 2.3 item 2 while the gate field is false, stock commands print the same text about stock's own commands and settings, and no stock MBean, metric or virtual table row changes. The three help entries and the settings row are additions inside a stock output. This spec reads such an addition, which leaves what stock prints about its own commands and settings as it is, as no change to a stock operation, and the merge of this spec approves that reading with the class too.

How this spec reads rule 7 against rule 1 of the feature switch rules of [branching-and-review.md](../../process/branching-and-review.md#feature-switches-and-defaults). Rule 1 gives every feature a nodetool toggle, and a toggle that works with the feature off needs an MBean registered with the feature off, so some memory of every feature exists in every state. This spec reads the words "no new memory is used" of rule 7, and of the stock behaviour rule of [quality-requirements.md](../../process/quality-requirements.md#stock-behaviour-unchanged), as no memory that grows with requests or data: with the switch off this feature holds only the fixed objects its switch, its counters and its version need, listed above, and allocates nothing per request beyond the JMX reply of a refused read. The merge of this spec approves that reading with the class. A maintainer who wants it in a decision record instead requests changes.

## 3. Feature requirements

FREQ-BVER-001 (event-driven): When the build runs the target `_createVersionPropFile`, the build SHALL write the entry `ChronitonDBVersion` into `version.properties`, after Apache's two entries, with the value `<Apache version>-chronitondb<n>`, with `<Apache version>` the build's `base.version` property and `<n>` the release number given as the trimmed value of the build property `chronitondb.release`. Source: decision record 0002 and the version numbers of release.md.

FREQ-BVER-002 (unwanted behaviour): If the build property `chronitondb.release` is not set, is empty or is made of white space only, then the build SHALL use `0` as `<n>`. Source: decision record 0002, whose `0` for a build given none this spec reads as covering an empty or white space only value.

FREQ-BVER-003 (unwanted behaviour): If the build property `chronitondb.release` is set to a value that is not a release number, then the target `_createVersionPropFile` SHALL fail the build with an error that names the property. Source: risk R2.

FREQ-BVER-004 (event-driven): When a JMX client reads the `Version` attribute of the `BuildVersion` MBean on a node whose switch is on, the node SHALL return the node's version. Source: decision record 0002.

FREQ-BVER-005 (event-driven): When a JMX client reads the `Version` attribute of the `BuildVersion` MBean on a node whose switch is off, the node SHALL refuse the read with an error that names the setting `build_version_command_enabled`. FREQ-BVER-006 (unwanted behaviour): If the node cannot read a `ChronitonDBVersion` entry, which is the case when and only when `version.properties` is absent from the class path, fails to load with an exception from opening or parsing it, has no such key or has an empty or white space only value for it, then the node SHALL take `Unknown` as the node's version. Source: the stock idiom of `FBUtilities.java:118` and `:473`, and risk R1.

FREQ-BVER-007 (event-driven): When an operator runs `nodetool chronitondbversion` against a node whose switch is on, the command SHALL print on stdout exactly one line, `ChronitonDBVersion: ` followed by the node's version, and nothing else. Source: decision record 0002.

FREQ-BVER-008 (event-driven): When an operator runs `nodetool chronitondbversion` against a node whose switch is off, the command SHALL print nothing on stdout. Source: the feature switch rules of branching-and-review.md, rule 7.

## 6. Compatibility

This feature changes no format, schema or protocol: the only new data is one entry inside `version.properties` on the class path, which stock code reads by key (`FBUtilities.java:465`) and never writes to disk or sends on the wire.

### 6.1 On-disk format changes

None.

### 6.2 Mixed-version cluster

Nodes never exchange the version, so a mixed cluster is a mix of nodetool and node builds only. A nodetool with this feature against a node without the MBean fails as nodetool fails on any missing MBean: nodetool turns the missing MBean into an `IllegalArgumentException` with the text `Server is not initialized yet, cannot run nodetool.` (`NodeTool.java:326` to `328`), thrown inside the catch block of `execute` and so left uncaught by it (`NodeTool.java:289` to `292`), which is why this one exception does not take the usage error path, and ends `main` (`NodeTool.java:85` to `87`) with the exception's stack trace on stderr and exit status 1. This feature leaves that as it is: it is stock's path, and no requirement of this feature governs it. A nodetool without this feature against a node with it refuses `chronitondbversion` through the stock usage error.

### 6.3 Upgrade path and prerequisites

No prerequisite for a node: it starts from any supported setup with the yaml key absent. On a cluster with JMX authorisation on, a role needs `SELECT` on the version MBean for `nodetool chronitondbversion` and `MODIFY` on it for the toggles, as for any MBean a role has no permission on (`AuthorizationProxy.java:422` to `427`).

### 6.4 Rollback path

Nothing to drop or rebuild. A rollback to a build without the feature removes the command and the MBean. An operator whose `cassandra.yaml` names `build_version_command_enabled` removes that key before the rollback, since a build without the feature refuses a yaml key it does not know (`YamlConfigurationLoader.java:422` to `423`). The reference page states this as a rollback prerequisite.

### 6.5 Runbook entries

One reference page for the feature, covering the command, the toggles, the setting, the MBean and the permissions it needs, the counters and the INFO lines, under `docs/` at the path that the design record of the item the plan gives `nodetool chronitondbversion` names, since the line has no documentation layout yet ([conventions.md](../../process/conventions.md#where-things-live), rule 3). The page carries the rollback prerequisite above. That item creates the page and `NEWS-chronitondb.txt`, which the sandbox line does not have, with the feature's entry, and each later item adds its own part to both.

## 7. Dependencies

No new dependency. The commands use airline, which nodetool already ships (`NodeTool.java:61`), and the counters use the stock metrics registry (`CassandraMetricsRegistry.java:55` to `58`).

## 9. Decisions

1. [0002. The shape of the build version command](../../decisions/0002-build-version-command-shape.md): one line from the node over JMX, `ChronitonDBVersion: ` followed by the version in the form `<Apache version>-chronitondb<n>` of release.md, with `0` as the release number of a build given none. The record places the entry next to Apache's `CassandraVersion`, in the same file, and leaves the line open. This spec fixes it after `GitSHA`, the last of Apache's two entries, for the reason of section 2.4, and the merge approves that position. This spec adds what the record leaves implicit: a release candidate carries the version of the release it becomes, since a candidate is promoted unchanged ([release.md](../../process/release.md#how-a-release-is-made)), and the `~rc<k>` suffix of release.md is a package version and never part of the entry. The release process of release.md names no build property today, so giving a candidate build its release number through `chronitondb.release` is a change to that process, which is not in the scope of section 1 and is for the maintainers. The feature is complete without it: until the process passes the property, every build prints `0`.

## 10. Milestones outline

1. Milestone 1, the whole feature as section 1 scopes it: the version entry, `BuildVersion` with its switch, gate field and lift, the three commands, the counters and the INFO lines. Its tests are JUnit tests and in-JVM distributed tests, since the line has no Cucumber runner for the scenarios of testing.md: in-JVM distributed tests over JMX against instances started with the GOSSIP and JMX features, with the switch on and with it off, and a JUnit test of FREQ-BVER-022 with the switch off, carried by the first item that edits `NodeTool.java` and run first at that item's base commit, the line commit its branch starts from, where it passes too. A validation item compares the output of `cassandra-stress version` on a build of the base commit of the item that adds the entry and on a build of that item's merge commit, with the same ant target and properties from a clean workspace (FREQ-BVER-026). The plan stage asks the maintainers the open point of section 2.5 item 6, which step makes the one line change that sets the gate field and whether it is an item of this plan, before the plan is written. The milestone makes the command testable end to end. The delivery plan gives the items.

## 11. Prior art

1. Stock Apache Cassandra 5.0 on this line. `nodetool version` asks the node over JMX and prints `ReleaseVersion: ` plus the node's release version, with `-v` adding `GitSHA: ` (`Version.java:36` to `38`, `NodeProbe.java:859` to `862`, `StorageServiceMBean.java:108`, `StorageService.java:3985` to `3988`). The node reads both values from `version.properties`, with `Unknown` when the file is missing (`FBUtilities.java:117` to `118` and `:460` to `474`), and the build writes that file (`build.xml:492` to `499`). `bin/cassandra -v` prints the local installation's version instead (`bin/cassandra:237`, `src/java/org/apache/cassandra/tools/GetVersion.java:24`). Right: the node's own version, one line, one source for the build and the node. Missing: no ChronitonDB version anywhere. This feature follows the same shape with the same properties file.
2. Apache Cassandra `cassandra-6.0` and `trunk`, `src/java/org/apache/cassandra/tools/nodetool/Version.java` at blob `9b39e19b3a`, read through the GitHub API, lines 39 to 44: nodetool moved to picocli, and `nodetool version -v` grew `BuildDate` and JVM lines. Apache keeps one line by default and puts more behind `-v`. This feature keeps the one line and adds no `-v`.
3. The ChronitonDB version numbers of [release.md](../../process/release.md#version-numbers), which that page describes as the pattern Ubuntu uses for packages it takes from Debian. This spec takes the form from release.md alone and cites no Debian or Ubuntu page. The command prints that package form, which says which build is installed. The string a node reports in `nodetool version`, `system.local` and gossip is a separate form for a separate purpose ([release.md](../../process/release.md#the-version-a-running-node-reports)), and this feature leaves it alone.
4. OpenSearch, read as code under the Apache License 2.0 from the default branch of `opensearch-project/OpenSearch` at commit `11a9090d5f` through the GitHub API. The root endpoint `GET /` answers from the node asked with the node's name, the cluster name and a `version` object that carries the distribution, the version number, the build type, hash and date, and the Lucene version (`server/src/main/java/org/opensearch/action/main/MainResponse.java` at blob `ad19241464`, lines 113 to 129). The server process started with `--version` or `-V` prints one line with the version, the build type, hash and date and the JVM version, then exits (`server/src/main/java/org/opensearch/bootstrap/OpenSearch.java` at blob `8e5f78642d`, lines 70 and 141 to 152). Right: a client asks the node for the node's own version, as here, and gets one answer with one fixed shape. Different: OpenSearch bundles the build hash and date with the version in both places, which stock `nodetool version -v` already prints here, so this feature keeps the version alone (decision record 0002).
