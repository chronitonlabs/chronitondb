## 1. Problem, acceptance criteria and requirements

An operator cannot tell which ChronitonDB build a node runs. `nodetool version` prints Apache Cassandra's version string, read from `org/apache/cassandra/config/version.properties` that the build writes (`src/java/org/apache/cassandra/utils/FBUtilities.java:443` to `465`, `build.xml:492` to `499`). During a rolling upgrade there is no way to ask a node whether it is on the new ChronitonDB release yet.

Acceptance criteria:

1. From the issue: an operator can ask a node, with nodetool, which ChronitonDB version it is running.
2. Derived from the issue's rolling upgrade case: asked with a ChronitonDB nodetool from this change on, the answer is the asked node's own, not the nodetool install's, so an upgrade can be checked node by node. An Apache Cassandra nodetool, or one from before this change, prints Apache's string for every node, because the choice is made in the nodetool process (`src/java/org/apache/cassandra/tools/nodetool/Version.java:33` to `39`), and the reference page says so (REQ-VER-032).

The maintainers settled the shape of the answer in release.md, What nodetool version shows, and in decision record 0002. `nodetool version` shows the release version, for example `5.0-chronitondb3`, on the stock `ReleaseVersion:` line, and the git SHA of the build on the stock `GitSHA:` line only with `--verbose`. No Apache release line appears. It is the one exception to the rule that a behaviour-changing feature is off by default (release.md item 1). It has a switch like every feature, on by default (item 2). The version and the git SHA are read from the build, never written into the code (item 3). `bin/cassandra -v`, the start log line `Cassandra version:` and the cqlsh banner stay as they are (item 5). No stock test changes (decision record 0002).

### How it works

Three parts, each small.

**1. The build writes the release version.** `build.xml` gains the property `chronitondb.version` next to `base.version` at `build.xml:36`, with the default `5.0-chronitondb-SNAPSHOT`. An Ant property set on the command line wins over one set in the file, so the release pipeline passes `-Dchronitondb.version=<version>` and needs no file change. The pipeline passes the release version, for example `5.0-chronitondb3`, because release.md, How a release is made, item 6 promotes the candidate unchanged, so the candidate build carries the release version it becomes. The build writes what it is given: a blank value reaches the node as `Unknown` (REQ-VER-007) and fails the build test of section 14. Every candidate of a release and the release itself print the same release version, because the candidate is what gets promoted: `5.0-chronitondb3~rc1` is the package version of a candidate (release.md, Version numbers), not what the node prints, and `--verbose` tells two candidates apart by their git SHA. The build does not check the value's form, and it does not refuse a release build without a value: Apache's own rpm build runs `ant artifacts -Drelease=true` on every build, snapshots included (`.build/docker/_build-redhat.sh:111` to `112`), and its spec builds with `-Dversion` and no `release` (`redhat/cassandra.spec:75`), so a guard on `release` would break stock build paths or miss the case. The form of the value is REQ-VER-033, which a test checks on the built file, and a release built without a value is caught by the release engineer's verification of the installed candidate (release.md, How a release is made, item 4), see problem 4.

The target `_createVersionPropFile` (`build.xml:492` to `499`) writes the stock file `org/apache/cassandra/config/version.properties` with the keys `CassandraVersion` and `GitSHA`. It gains one more entry, `ReleaseVersion`, with the value of `chronitondb.version`. The stock target already creates the directory (`build.xml:494`), git already ignores it (`.gitignore:8`), `clean` already deletes it (`build.xml:419`), the source artifact already excludes it (`build.xml:949`), `build-project` already copies it into the classes directory (`build.xml:544` to `547`) and the IDE already reads it from `src/resources`. One entry in the existing file needs none of that again. The stock readers of the file, `FBUtilities.getReleaseVersionString()` and `getGitSHA()`, read their own keys and ignore the rest (`FBUtilities.java:460` to `474`), so nothing stock changes. The default exists because Ant needs the property defined for the entry. It is a build detail, documented on the reference page, not a requirement.

**2. The node exposes the value over JMX.** The class `org.chronitondb.version.ReleaseVersion` reads the file once from the classpath, at its first use, as `FBUtilities.loadedProperties` does (`FBUtilities.java:443` to `458`). It returns the value of `ReleaseVersion` after `String.trim()`, or `FBUtilities.UNKNOWN_RELEASE_VERSION`, the string `Unknown` (`FBUtilities.java:117`), when the file or the key is missing, the value is blank after trimming, or the load throws. As the stock loader does (`FBUtilities.java:443` to `458`), it catches every exception of the load, logs one WARN line and returns `Unknown`, so a bad file never stops a node from starting. The loader of `FBUtilities` is private, so the fork reads the file with its own few lines.

The MBean `org.chronitondb:type=ReleaseVersion` is the class `org.chronitondb.version.ReleaseVersionReporter`, which implements `ReleaseVersionReporterMBean`, named as the JMX Standard MBean rules require and as every stock MBean is named, for example `StorageService implements StorageServiceMBean` (`src/java/org/apache/cassandra/service/StorageService.java:293`). It exposes the read only attribute `ReleaseVersion` and the writable attribute `Enabled`. It holds the counter `Reported` in a final field, registered once through `CassandraMetricsRegistry.Metrics.counter` (`src/java/org/apache/cassandra/metrics/CassandraMetricsRegistry.java:55`) with a `MetricName` built by the five argument constructor (`CassandraMetricsRegistry.java:818`), group `org.chronitondb.metrics`, type `ReleaseVersion`, name `Reported`, no scope, and the MBean name `org.chronitondb.metrics:type=ReleaseVersion,name=Reported` written out, as `DefaultNameFactory.createMetricName` does for stock (`src/java/org/apache/cassandra/metrics/DefaultNameFactory.java:47` to `50`). The four argument constructor quotes every part of the name (`CassandraMetricsRegistry.java:803` to `806`), so it is not used.

`register()` is two lines: `MBeanWrapper.instance.registerMBean(this, NAME, OnException.LOG)` (`src/java/org/apache/cassandra/utils/MBeanWrapper.java:90`), then the INFO line with the release version, on every call, so the start log always carries the value and, when the registration failed, the wrapper's ERROR line sits right beside it. `NAME` is a constant on the interface `ReleaseVersionReporterMBean`, which nodetool reads too, so the nodetool process never loads the reporter class or creates its counter. The wrapper catches every exception of the registration and hands it to `OnException.LOG`, which writes `Error in MBean wrapper:` at ERROR (`MBeanWrapper.java:176` to `185` and `366`), so a registration failure is logged and the node goes on starting with no catch in fork code. `StorageService.initServer` calls `register()` right after its own `registerMBeans()` (`StorageService.java:1018`), so the fork MBean appears from the same point in a start as the stock `StorageService` MBean, a few lines later. Before that point stock `nodetool version` fails too, with `Server is not initialized yet` (`src/java/org/apache/cassandra/tools/NodeTool.java:327` to `328`). A second pass through `initServer` throws at the stock registration before the hook line, because the stock call passes a `String` name (`StorageService.java:501` and `562`) to the overload that uses `OnException.THROW` (`MBeanWrapper.java:99` to `102`), so `register()` never runs twice on a node and needs no guard.

The switch is the yaml key `nodetool_release_version_enabled`, a new `volatile boolean` field of `Config` with the default `true`, read and written through `DatabaseDescriptor.getRawConfig()` (`src/java/org/apache/cassandra/config/DatabaseDescriptor.java:385`). The setter of `Enabled` logs the old and the new value at INFO on every write, as `StorageService.setCompactionThroughputMbPerSec` does (`StorageService.java:1925` to `1933`). The MBean stays registered while the switch is off, so the toggle can turn the feature on at runtime. The `ReleaseVersion` attribute returns the value whatever the switch says: the switch decides what nodetool prints, not what JMX shows. The start log line reads the value from the class `org.chronitondb.version.ReleaseVersion` directly, not through the attribute, so the counter is 0 after start.

**3. nodetool asks the node.** The stock command `version` (`src/java/org/apache/cassandra/tools/nodetool/Version.java:25` to `39`) gets one hook line at the top of `execute`: `if (VersionOutput.print(probe, verbose)) return;`. The command then ends in one of three ways: the fork lines, the stock lines, or a failure reported as stock reports it. The stock lines come in four cases.

The fork class `org.chronitondb.tools.nodetool.ReleaseVersionProbe` finds the MBean on the probe's connection, `NodeProbe.getMbeanServerConn()` (`src/java/org/apache/cassandra/tools/NodeProbe.java:772`), with `isRegistered` and then a `JMX.newMBeanProxy`. `VersionOutput.print` returns `false`, and the stock lines run unchanged with nothing on standard error, when:

1. The probe has no connection, `getMbeanServerConn()` returns `null`. That is the in-JVM distributed test framework, whose `InternalNodeProbe.connect` sets the field to `null` and points the proxies at the node's own singletons (`test/distributed/org/apache/cassandra/distributed/mock/nodetool/InternalNodeProbe.java:61` to `70`). The stock distributed test `NodeToolTest` runs nodetool that way, so it prints stock output and passes unchanged.
2. The MBean is absent: the node runs Apache Cassandra or an older ChronitonDB build.
3. `Enabled` is `false`.
4. The connection throws `SecurityException` on the lookup or on the read of `Enabled` or `ReleaseVersion`, because the authorization proxy of section 10 lets the role read `StorageService` but not this MBean. The role sees what it is allowed to see, which is the stock output. In the other two access modes of section 10 an open connection answers the reads: no access control applies when neither the proxy nor the access file is set, and a user the JDK access file admits reads both attributes. A user the file does not admit is refused every call, the stock reads too, so `nodetool version` ends on the stock error path there, as it does today.

Any other exception from the lookup or the reads, for example the `IOException` that `MBeanServerConnection.isRegistered` declares, is wrapped in a `RuntimeException` with the original as its cause, because `Version.execute` declares no checked exception (`Version.java:33` to `34`). `NodeTool.execute` catches it, prints `error: ` with the root cause to standard error and returns status 2 (`NodeTool.java:289` to `292` and `329` to `334`), as it does when a stock call fails on the same connection. One root cause takes a different stock path: `InstanceNotFoundException`, the MBean unregistered between the lookup and the read, which `NodeTool.err` turns into `IllegalArgumentException("Server is not initialized yet, cannot run nodetool.")` thrown out of `execute` from inside its catch (`NodeTool.java:327` to `328`), exactly as for a stock call against a node that is still starting. The fork wraps the checked exception with the original as its cause, so `Throwables.getRootCause` finds it as it does for stock. REQ-VER-022, REQ-VER-030 and REQ-VER-031 leave that case to stock, and `VersionOutputStubTest` does not test it, since the fork code adds nothing to it. Otherwise `print` writes the release version line, with `--verbose` the git SHA line from the stock `probe.getGitSHA()` (`NodeProbe.java:864` to `867`), and returns `true`.

Two new commands, `enablereleaseversion` and `disablereleaseversion`, use `ReleaseVersionProbe` to set `Enabled`. Stock's generic `nodetool sjk` can reach any MBean over the probe's connection (`src/java/org/apache/cassandra/tools/nodetool/Sjk.java:67`, listed at `NodeTool.java:224`), but branching-and-review.md item 1 asks for a nodetool toggle for every feature, and every stock toggle is a named pair that `nodetool help` lists, so the record follows that idiom. They are added to the command list in `src/java/org/apache/cassandra/tools/NodeTool.java:98` to `246`, next to `Version.class` at line 243. They print nothing on success, as `disableauditlog` does (`src/java/org/apache/cassandra/tools/nodetool/DisableAuditLog.java:25` to `35`). They have one failure path of their own, the usage error path: `ReleaseVersionProbe` throws `IllegalStateException` with a message naming the command, which `NodeTool.execute` sends to `badUse`, `nodetool: <message>` and then `See 'nodetool help' or 'nodetool help <command>'.` on standard output, and returns status 1 (`NodeTool.java:277` to `288` and `318` to `322`). `execute` returns the status and only `main` calls `System.exit` (`NodeTool.java:85` to `87`), so the in-JVM framework, which calls `execute`, survives it. `VersionOutputStubTest` proves it in process for REQ-VER-012, REQ-VER-013, REQ-VER-023 and REQ-VER-024. When `isRegistered` answers `false` the message is `enablereleaseversion: the node has no ChronitonDB release version reporter. It runs Apache Cassandra or an older ChronitonDB build, or the reporter failed to register at start.`, and when the probe has no connection it is `enablereleaseversion needs a JMX connection`, each with `disablereleaseversion` in its place for the other command. When the lookup or the write throws, `SecurityException` for a role without `DESCRIBE` or `MODIFY` on the MBean, or the `IOException` the connection declares, the toggle ends on the stock error path, `error: ` with the root cause on standard error and status 2, the checked exception wrapped as for `version` (REQ-VER-030, REQ-VER-031). The Debian shell completion list stays as it is: release.md, Packaging, item 5 keeps Apache's `debian/` folder untouched, and the fork's own packaging carries its completion, see section 15.

The output when the switch is on, as decision record 0002 settles it:

```
$ nodetool version
ReleaseVersion: 5.0-chronitondb3
$ nodetool version --verbose
ReleaseVersion: 5.0-chronitondb3
GitSHA: 1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b
```

Stock prints `ReleaseVersion: 5.0.10` on a release build, `ReleaseVersion: 5.0.10-SNAPSHOT` on any other build, and with `--verbose` a second line `GitSHA: <sha>` (`Version.java:36` to `38`, `build.xml:104` to `107`). "Stock output" in this record means what the stock code of `Version.execute` writes on standard output and on standard error, and the status `NodeTool.execute` returns, on the same node over the same connection, from `StorageServiceMBean.getReleaseVersion()` and `getGitSHA()`: on a connection that answers both reads, the one or two lines, nothing on standard error and status 0, and on a connection that refuses them, for example a role without `SELECT` on `StorageService` under the authorization proxy, the stock error path. REQ-VER-003, REQ-VER-004, REQ-VER-020 and REQ-VER-021 ask for both streams and the status, and their tests compare both streams and the status. The stock distributed test `NodeToolTest.testVersionIncludesGitSHAWhenVerbose` asserts that `version` prints no `GitSHA:` line and `version --verbose` does (`test/distributed/org/apache/cassandra/distributed/test/NodeToolTest.java:137` to `149`). Decision record 0002 keeps both assertions true with no change to that test.

The milestone gate rule, that a switch refuses to turn on before the feature's final milestone gate ([additive.md, Milestone gates](../../process/additive.md#milestone-gates)), binds a feature with milestones. This item has no milestone, so the maintainer's merge of the code pull request (maintenance.md, The one-item path, item 4) counts as its final gate, and from that merge the switch works: release.md item 3 says the feature blocks the line's first release until it is in, and release.md, What a release may contain, item 4 says its switch is on by default in every release of the line. Nothing refuses to turn it on.

### Requirements

REQ-VER-001 (event driven): When `nodetool version` runs without `--verbose` against a node that has the MBean and whose switch is on, over a connection that answers the lookup and the reads, nodetool MUST print exactly one line to standard output, `ReleaseVersion: ` followed by that node's release version. Source: acceptance criterion 1 and decision record 0002.

REQ-VER-002 (event driven): When `nodetool version --verbose` runs against a node that has the MBean and whose switch is on, over a connection that answers the lookup and the reads, nodetool MUST print exactly two lines to standard output, the line of REQ-VER-001 and then `GitSHA: ` followed by the value of `StorageServiceMBean.getGitSHA()` of that node. Source: decision record 0002.

REQ-VER-003 (state driven): While the node's switch is off, nodetool MUST print, for `nodetool version` with or without `--verbose` over a connection that answers the lookup and the read of `Enabled`, exactly the stock output as defined in section 1. Source: problem 1, under the stock behaviour rule of quality-requirements.md.

REQ-VER-004 (unwanted behaviour): If the node asked has no MBean `org.chronitondb:type=ReleaseVersion`, then nodetool MUST print, for `nodetool version` with or without `--verbose`, exactly the stock output as defined in section 1. Source: problem 8.

REQ-VER-005 (event driven): When nodetool prints the release version line of REQ-VER-001, the value MUST be the one the asked node's attribute `ReleaseVersion` returned over the connection. Source: acceptance criterion 2.

REQ-VER-006 (ubiquitous): The node MUST read its release version from the key `ReleaseVersion` of the classpath resource `org/apache/cassandra/config/version.properties`, with `String.trim()` applied. Source: acceptance criterion 1, as release.md item 3 shapes it: read from the build.

REQ-VER-007 (unwanted behaviour): If the resource `org/apache/cassandra/config/version.properties` is missing, cannot be loaded, lacks the key `ReleaseVersion`, or holds a value that is empty after `String.trim()`, then the attribute `ReleaseVersion` MUST return `Unknown`. Source: problem 4.

REQ-VER-008 (ubiquitous): The yaml key `nodetool_release_version_enabled` MUST default to `true`. Source: acceptance criterion 1, as release.md item 2 shapes it: on by default, nothing to configure first.

REQ-VER-009 (event driven): When `nodetool enablereleaseversion` runs against a node with the MBean, the node MUST set the in-memory value of `nodetool_release_version_enabled` to `true`. Source: problem 10.

REQ-VER-010 (event driven): When `nodetool disablereleaseversion` runs against a node with the MBean, the node MUST set the in-memory value of `nodetool_release_version_enabled` to `false`. Source: problem 10.

REQ-VER-011 (event driven): When the attribute `Enabled` of the MBean is written, the node MUST log one INFO line with the old and the new value. Source: problem 7.

REQ-VER-012 (unwanted behaviour): If `nodetool enablereleaseversion` runs against a node with no MBean `org.chronitondb:type=ReleaseVersion`, then nodetool MUST end on the usage error path with the message `enablereleaseversion: the node has no ChronitonDB release version reporter. It runs Apache Cassandra or an older ChronitonDB build, or the reporter failed to register at start.` Source: problem 8.

REQ-VER-013 (unwanted behaviour): If `nodetool disablereleaseversion` runs against a node with no MBean `org.chronitondb:type=ReleaseVersion`, then nodetool MUST end on the usage error path with the message `disablereleaseversion: the node has no ChronitonDB release version reporter. It runs Apache Cassandra or an older ChronitonDB build, or the reporter failed to register at start.` Source: problem 8.

REQ-VER-014 (event driven): When `StorageService.initServer` runs, the node MUST register the MBean `org.chronitondb:type=ReleaseVersion` through `MBeanWrapper.instance`. Source: problem 6.

REQ-VER-015 (event driven): When `ReleaseVersionReporter.register()` runs, the node MUST log one INFO line `ChronitonDB release version: ` followed by its release version. Source: problem 7.

REQ-VER-016 (unwanted behaviour): If registering the MBean throws, then `register()` MUST return without throwing. Source: problem 3.

REQ-VER-017 (event driven): When the attribute `ReleaseVersion` of the MBean is read, the node MUST increment the counter `Reported` of the metric type `ReleaseVersion` by one, whatever the switch says. Source: problem 7.

REQ-VER-018 (ubiquitous): The node MUST keep returning Apache Cassandra's build version from `StorageServiceMBean.getReleaseVersion()`, with the switch on and off. Source: problem 9.

REQ-VER-019 (state driven): While the switch is off, the MBean `org.chronitondb:type=ReleaseVersion` MUST stay registered. Source: problem 10.

REQ-VER-020 (unwanted behaviour): If the JMX connection throws `SecurityException` while nodetool looks the MBean up or reads `Enabled` or `ReleaseVersion`, then nodetool MUST print, for `nodetool version` with or without `--verbose`, exactly the stock output as defined in section 1. Source: problem 5.

REQ-VER-021 (unwanted behaviour): If the probe has no JMX connection, then nodetool MUST print, for `nodetool version` with or without `--verbose`, exactly the stock output as defined in section 1. Source: problem 5.

REQ-VER-022 (unwanted behaviour): If the JMX connection throws an exception other than `SecurityException`, and other than one whose root cause is `InstanceNotFoundException`, while nodetool looks the MBean up or reads `Enabled` or `ReleaseVersion`, then `nodetool version` MUST end on the stock error path. Source: problem 5.

REQ-VER-023 (unwanted behaviour): If `nodetool enablereleaseversion` runs with no JMX connection, then nodetool MUST end on the usage error path with the message `enablereleaseversion needs a JMX connection`. Source: problem 5.

REQ-VER-024 (unwanted behaviour): If `nodetool disablereleaseversion` runs with no JMX connection, then nodetool MUST end on the usage error path with the message `disablereleaseversion needs a JMX connection`. Source: problem 5.

## 4. Prior art reviewed

Stock Apache Cassandra, read on this line at the Apache base commit:

1. The build writes `CassandraVersion` and `GitSHA` into `version.properties` under `src/resources` at `build.xml:492` to `499`, from `version` (`base.version` or `base.version-SNAPSHOT`, lines 104 to 107) and `git.sha` (`.build/build-git.xml:22` to `41`, `git describe --always --dirty`, `Unknown` without git), creates the directory first (line 494), ignores it in git (`.gitignore:8`), deletes it in `clean` (line 419) and keeps it out of the source artifact (line 949). The design adds one entry to that file and reuses all of it.
2. `FBUtilities.getReleaseVersionString()` and `getGitSHA()` read the file once through a memoized supplier and return `Unknown` when it is missing (`FBUtilities.java:443` to `474`). The loader is private and reads only its own two keys, so the design copies the shape and uses the stock constant `UNKNOWN_RELEASE_VERSION` (`FBUtilities.java:117`).
3. `nodetool version` is three lines of code over two MBean getters (`Version.java:33` to `39`, `NodeProbe.java:859` to `867`, `StorageServiceMBean.java:108` and `114`). The design leaves them in place and adds one line before them.
4. Stock boolean toggles are command pairs: `enableauditlog` and `disableauditlog` (`DisableAuditLog.java:25` to `35`), `enablebinary` and `disablebinary`, `enablegossip` and `disablegossip`. The design follows the pair idiom. A command that finds its precondition false prints a line to `probe.output().out` and exits 1, as `Status` does (`Status.java:59` and `89` to `96`). A command that cannot run at all throws `IllegalStateException`, which `NodeTool.execute` reports as a usage error with status 1 (`NodeTool.java:277` to `288`), and any other failure is `error:` with status 2 (`NodeTool.java:289` to `292`).
5. A runtime setting is a `volatile` field of `Config` written through a setter that logs the old and the new value at INFO on every write, for example `StorageService.setCompactionThroughputMbPerSec` (`StorageService.java:1925` to `1933`). The design follows it with one field and the MBean setter.
6. `MBeanWrapper.registerMBean(obj, name, OnException.LOG)` catches every registration failure and logs it at ERROR (`MBeanWrapper.java:90`, `176` to `185`, `366`). The stock `StorageService` registration uses `OnException.THROW` (`MBeanWrapper.java:99` to `102`), which is why `initServer` cannot run twice. The design uses `LOG` and adds no catch and no guard of its own.
7. Apache's yaml loader refuses a key it does not know, `Invalid yaml. Please remove properties ... from your cassandra.yaml` (`YamlConfigurationLoader.java:321` and `423`). So the key is a `Config` field, and the rollback line in section 9 exists.
8. JMX authorization: `AuthorizationProxy` maps `isRegistered` to the `DESCRIBE` permission, `getAttribute` to `SELECT` and `setAttribute` to `MODIFY` on the target MBean (`src/java/org/apache/cassandra/auth/jmx/AuthorizationProxy.java:418` to `437`) and throws `SecurityException("Access Denied")` without a grant (`AuthorizationProxy.java:179`). A role granted `StorageService` only would fail on the fork MBean, which is why REQ-VER-020 exists.
9. The in-JVM distributed test framework runs nodetool through `new NodeTool(new InternalNodeProbeFactory(...), output).execute(args)` (`test/distributed/org/apache/cassandra/distributed/impl/Instance.java:1080`) with a probe that has no JMX connection (`InternalNodeProbe.java:61` to `70`), which is why REQ-VER-021, REQ-VER-023 and REQ-VER-024 exist, and the pattern the stub test of section 14 follows.
10. Stock metric names are built with the five argument `MetricName` constructor and an unquoted MBean name (`DefaultNameFactory.java:47` to `50`, `CassandraMetricsRegistry.java:818`). The design does the same under the fork group.
11. Apache trunk and the 6.0 line: `nodetool version` has the same shape, on picocli instead of airline, so a 6.0 port writes the two toggle commands again in picocli. Not part of this item.
12. Apache JIRA: CASSANDRA-17753 added the `GitSHA` line and the stock test that asserts it (commit `230fe8e647`). Its comments put the line behind `--verbose` because a released build is fixed to one SHA, so the SHA is a development detail that should not reach the plain user facing output. Decision record 0002 keeps that rule.

Other systems, by behaviour from their public documentation:

1. OpenSearch, a fork of another search engine, reports its own version number in the same field its base product used, `version.number` of `GET /`, and adds a `distribution: opensearch` field beside it. The fork's version takes the existing field, and the base product's version is not shown.
2. Ubuntu reports its own release through `lsb_release -a` and `/etc/os-release`, never the Debian version it was built from. A downstream distribution names itself.
3. Keeping Apache's line next to a new one was considered and not taken: the maintainers settled on no Apache release line (release.md). The reason stands: a ChronitonDB line carries Apache fixes ahead of an Apache release and can lag or lead the Apache patch release its build version names, so an Apache line would name a release the node does not contain exactly.

No patents were searched or read.

## 5. Idiom and consistency

User visible choices and what each follows:

1. **The two lines of `nodetool version` on a ChronitonDB node, settled by decision record 0002.** `ReleaseVersion: <release version>`, and `GitSHA: <sha>` only with `--verbose`. Stock match: the labels, the flag and the line count do not change, only the first value. Earlier decision match: release.md names the value "the release version" and says the command shows the git SHA, which it does under the stock flag. Idiom: the Ubuntu and OpenSearch pattern, the fork's version in the existing field. OpenSearch equivalent: `version.number`, which carries OpenSearch's own number by default, and `build_hash`, always present. The two options not taken are in the decision record: both lines always, which changes the line count and makes the stock assertion `stdoutNotContains("GitSHA:")` at `NodeToolTest.java:143` fail, and a new label `ChronitonDB:`, which a script that reads `ReleaseVersion:` would not find.
2. **The yaml key `nodetool_release_version_enabled`, default `true`.** Stock match: the `<thing>_enabled` form of `hinted_handoff_enabled` (`Config.java:112`). Earlier decision match: release.md item 2, a switch on by default. Idiom: conventions.md, a setting named for what it does, no `cassandra` or `axon` in it. OpenSearch equivalent: none, the version output has no switch there.
3. **The commands `enablereleaseversion` and `disablereleaseversion`.** Stock match: the enable and disable pairs, silent on success. Earlier decision match: branching-and-review.md, Feature switches and defaults, item 1 asks for a nodetool toggle. Idiom: lower case, no separator, as every stock command. OpenSearch equivalent: none.
4. **The toggles' failure against a node without the MBean, or without a connection: the usage error path, `nodetool: ` and a line naming the command on standard output, status 1.** Stock match: `NodeTool.execute` prints `IllegalStateException` that way (`NodeTool.java:277` to `288` and `318` to `322`), and no `System.exit` runs. Earlier decision match: quality-requirements.md, an error names the toggle that controls the behaviour. Idiom: a command that cannot do its work is a usage error with status 1, a broken connection is `error:` and status 2. OpenSearch equivalent: none, a command line toggle has no counterpart there.
5. **The MBean `org.chronitondb:type=ReleaseVersion` with `ReleaseVersion` and `Enabled`.** Stock match: `StorageServiceMBean` exposes `ReleaseVersion` as a read only attribute. Earlier decision match: conventions.md, the domain `org.chronitondb`. Idiom: one MBean per feature, the attribute named as stock names the same value. OpenSearch equivalent: `GET /` field `version.number`.
6. **The metric `org.chronitondb.metrics:type=ReleaseVersion,name=Reported`.** Stock match: a Dropwizard counter through `CassandraMetricsRegistry.Metrics.counter` (`CassandraMetricsRegistry.java:55`), with a `MetricName` from the five argument constructor (`CassandraMetricsRegistry.java:818`) as `DefaultNameFactory` builds stock names. Earlier decision match: conventions.md, fork metrics use their own types and stock types gain nothing. Idiom: a counter's name is a past participle. OpenSearch equivalent: none.
7. **The build value `5.0-chronitondb-SNAPSHOT` for a build made without `chronitondb.version`.** Stock match: `base.version-SNAPSHOT` for a build without `-Drelease` (`build.xml:107`). Earlier decision match: release.md, Version numbers, a release version never carries an Apache patch number, so none is in it. Idiom: Apache's own word for an unreleased build. OpenSearch equivalent: `-SNAPSHOT` on unreleased builds. No process page names the value, so the maintainers approve it with this record.
8. **The word `Unknown`.** Stock match: `FBUtilities.UNKNOWN_RELEASE_VERSION` (`FBUtilities.java:117`), reused, not copied. Earlier decision match: none touches it. Idiom: stock's own word for a missing build value. OpenSearch equivalent: none, its build never lacks the value.
9. **Stock output, and nothing else, under a JMX role without a grant on the fork MBean, under the authorization proxy.** Stock match: the role gets exactly what it got before the change, on standard output and standard error alike. Earlier decision match: the stock behaviour rule, which binds this case with the switch off too, since the lookup runs before the switch is known. Idiom: a permission decides what a caller sees, it does not make an allowed call fail. The reference page names the three JMX access modes of section 10 and tells an operator who uses the authorization proxy which permissions to grant: `DESCRIBE` and `SELECT` to see the release version, `DESCRIBE` and `MODIFY` for the commands (REQ-VER-028). OpenSearch equivalent: none, a denied `GET /` is a 403 error there and nothing is shown.

## 10. Threat model and security

New entry points, each checked with STRIDE:

1. **The yaml key.** Input: a boolean parsed by snakeyaml into a `Config` field, like every other key. Bound: `true` or `false`, anything else fails yaml loading as stock does. Spoofing, tampering, repudiation: the file is the operator's, as every key. Information disclosure, denial of service, elevation: none, the key picks one of two output values. No mitigation needed beyond stock, no permission.
2. **The MBean `org.chronitondb:type=ReleaseVersion`.** Input: `setEnabled(boolean)` over JMX. Bound: a boolean. Spoofing and elevation: the MBean sits under the JMX access mode of the node, which stock sets in one of three ways, and it adds no mode and no permission of its own. No access control applies to any MBean when neither `cassandra.jmx.authorizer` nor the access file is set, with authentication on or off (`src/java/org/apache/cassandra/utils/JMXServerUtils.java:110` to `114` and `218` to `226`), which is the case on the stock default of local JMX with authentication off (`conf/cassandra-env.sh:228` to `239`): whoever the connector admits reads and writes this MBean as every stock one. The JDK access file: when `com.sun.management.jmxremote.access.file` names one and no authorizer is set, stock hands the file to the connector (`JMXServerUtils.java:218` to `226`) and the JDK applies it to every MBean by user, as its documentation says: a `readonly` user reads `ReleaseVersion` and `Enabled`, so `nodetool version` works, and may not write `Enabled`, so the toggles end on the stock error path, `error: ` with the refusal text of the JDK's own access controller, which this record does not quote, and status 2 (REQ-VER-030, REQ-VER-031), and a `readwrite` user does both. The authorization proxy: when `cassandra.jmx.authorizer` is set (`JMXServerUtils.java:209` to `217`), the stock `AuthorizationProxy` guards every MBean by name (`AuthorizationProxy.java:79`, `144` and `192`), and a role needs the stock `DESCRIBE` permission for the lookup, `SELECT` for the reads and `MODIFY` for the setter on this MBean (`AuthorizationProxy.java:418` to `437`), no new permission. The proxy enforces those grants only where they apply, as for every stock MBean: it admits every call when the authorizer requires no authorization (`AuthorizationProxy.java:204` to `206`), a call with no subject, the connector's own (`AuthorizationProxy.java:208` to `210`), and every call of a superuser role (`AuthorizationProxy.java:229` to `231`), and a grant on the JMX root resource covers this MBean with every other (`AuthorizationProxy.java:391` to `393`). A role without them gets `SecurityException`: the toggles end on the stock error path, as any stock command without a grant, and `nodetool version` prints the stock output (REQ-VER-020). The grants of REQ-VER-028 hold in this mode only, and the reference page says so. The stock `AuthorizationProxyTest` runs unchanged as the proof that the proxy guards MBeans by name, `JMXAuthTest` runs it unchanged behind a real connector (`test/unit/org/apache/cassandra/auth/jmx/JMXAuthTest.java:89` to `97`), and `VersionOutputStubTest` proves REQ-VER-020. Information disclosure: with remote JMX on, the attribute is readable by whoever the access mode admits, with no access to the host. Stock already exposes Apache's version string and the git SHA of the build over the same connection, `StorageServiceMBean.getReleaseVersion()` and `getGitSHA()` (`src/java/org/apache/cassandra/service/StorageServiceMBean.java:108` and `114`), so the release version is a third string of the same kind, and under the authorization proxy it sits behind its own grant on the fork MBean, which a role granted `StorageService` alone does not have. Repudiation: the INFO line of every write records what changed and when, not which JMX user changed it, as the stock setters of `StorageService` do (`StorageService.java:1925` to `1933`). Repudiation is accepted at the stock level. Denial of service: reading one string cannot load the node. Tampering: the setter writes one boolean of the running node, gone at restart.
3. **The two nodetool commands.** Input: none, no arguments. They call the setter above under the same JMX rules.
4. **The properties file.** Input: a classpath resource inside the jar the build wrote, the stock file with one more key. An attacker who can replace a jar can replace any class, so the key adds no new surface.

Audit entries: the INFO lines of section 8. Limits: none, no threshold exists. Errors to client errors: none, there is no client. The toggle against a node without the MBean fails with exit code 1 and the line of REQ-VER-012 or REQ-VER-013.

## New terms

1. **Release version**: the ChronitonDB version of an installed build, `<line>-chronitondb<n>` as release.md, Version numbers, defines it, `5.0-chronitondb-SNAPSHOT` on a build made without one, or `Unknown` when the build wrote none or a blank. In code the class `org.chronitondb.version.ReleaseVersion`, in docs "release version".
2. **Stock output**: what the stock code of `Version.execute` writes on standard output and on standard error, and the status it returns, on the same node over the same connection, defined in section 1.
3. **Release version reporter**: the node side object behind the MBean `org.chronitondb:type=ReleaseVersion`. In code `ReleaseVersionReporter`, in the messages of REQ-VER-012 and REQ-VER-013 "release version reporter".
4. **Usage error path**: `NodeTool.execute` prints `nodetool: ` and the message, then `See 'nodetool help' or 'nodetool help <command>'.`, on standard output and returns status 1 (`NodeTool.java:277` to `288` and `318` to `322`). Nothing on standard error, and no call of `System.exit`: `main` alone exits, with the status `execute` returned (`NodeTool.java:85` to `87`).
5. **Stock error path**: `NodeTool.execute` prints `error: ` and the message of the root cause, then its stack trace, on standard error and returns status 2 (`NodeTool.java:289` to `292` and `330` to `332`).

## Where problems could occur

1. **A script that parses `nodetool version` reads a ChronitonDB value where it expected an Apache one.** Seen by an operator whose tooling compares the first line with an Apache version pattern, on every node with the switch on, which is every node by default. From the output change of REQ-VER-001. Decision record 0002 settles the line, and the switch is the way out for an operator who needs the old line.
2. **A node rolled back to an Apache Cassandra binary, or to an older ChronitonDB build, does not start.** Seen as `Invalid yaml. Please remove properties [nodetool_release_version_enabled] from your cassandra.yaml` at start, on a node whose operator wrote the key into the yaml. From the new `Config` field. Not from the default: a yaml that never names the key loads on both binaries.
3. **The MBean registration throws.** Seen as an ERROR line at start and stock output from every nodetool. From the hook in `StorageService`. The stock wrapper turns a failure into a logged error (`MBeanWrapper.java:176` to `185`), and REQ-VER-016 pins that.
4. **The build writes a wrong, blank or missing value, or a release build ships the snapshot value.** Seen as `ReleaseVersion: Unknown`, a value the pipeline did not intend, or `5.0-chronitondb-SNAPSHOT` on an installed release. From the `build.xml` edit or a pipeline passing the wrong property or none. REQ-VER-007, REQ-VER-025 and REQ-VER-033 make the missing, blank and malformed cases visible rather than a crash or a blank line. A release build without a value is caught by the release engineer's verification of the installed candidate, which no test on this line can make.
5. **`nodetool version` fails, or quietly prints Apache's version, where stock worked.** Seen as `error: Access Denied` from nodetool, by a JMX role that may read `StorageService` but not the fork MBean, against ChronitonDB and Apache nodes alike, since the lookup runs before the node kind is known. Seen as a `NullPointerException`, or a `System.exit` inside the test JVM, in the in-JVM distributed tests, where the probe has no connection. Seen as Apache's version, with nothing to say why, by an operator whose role was not granted the fork MBean, or who asks with an Apache Cassandra nodetool or one from before this change, and who then cannot tell a node that is not upgraded from a grant or a nodetool that is old. From the `isRegistered` and `getAttribute` calls in `ReleaseVersionProbe`. REQ-VER-020 and REQ-VER-021 turn the first two into stock output, REQ-VER-022 keeps every other failure as stock reports it, REQ-VER-012, REQ-VER-013, REQ-VER-023 and REQ-VER-024 keep the toggles on the usage error path, which never exits the JVM, REQ-VER-030 and REQ-VER-031 keep their failures on the stock error path, and REQ-VER-028 and REQ-VER-032 tell the operator which permissions the role needs and which nodetool to use.

From `ReleaseVersionReporter` and its interface name. REQ-VER-014 pins the registration on the platform server, which validates both.
